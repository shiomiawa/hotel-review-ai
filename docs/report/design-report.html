設計書レポート　口コミAI分析＆返信支援アプリ

作成者：shiomiawa 公開URL：https://hotel-review-ai.vercel.app GitHub：https://github.com/shiomiawa/hotel-review-ai
ホテル・旅館の口コミCSVを読み込み、4つの視点で分析して「優先して改善すべき点」と「強み」を示すWebアプリ。 返信文の下書き作成は、分析と改善に時間を回すための補助機能として位置づける。

1. 背景と解決したい課題

  • 現場スタッフは口コミを見ても「返信文をどう書くか」に意識を取られ、口コミを業務改善に結び付けられていない。
  • 特に「大変親切な接客でした」のような一言の好評口コミへの返信に迷い、時間がかかっている。
  • コンセプト：返信に悩む時間を、改善と接客に戻す。アプリの主役は「分析」とし、画面の並び順や見出しでも分析を先に大きく扱う。

2. 利用者と毎日の運用

利用者ホテル・旅館の支配人、フロントスタッフ（宿泊の大半は1泊。観光・出張・家族旅行など）
いつ使うか毎日夕方の決まった時間
流れ① OTA管理画面や口コミ管理サービスから口コミCSVを取り出す → ② アプリに読み込む → ③ ボタン1つで分析 → ④ 現場スタッフへ日次メールを送る
設計思想データを取りに行くのはオーナー。アプリは渡されたCSVを分析するだけ（自動収集はしない）。

5. システム構成

5.（続き）使う技術と選んだ理由

技術（用途）選んだ理由
Next.js 16・TypeScript（画面とサーバー処理）画面とAPI（サーバー側処理）を1つのプロジェクトで作れ、Vercelにそのまま公開できる。型でデータの形の食い違いを防ぐ。
Tailwind CSS（見た目）スマホ幅・ダークモードへの対応を少ない記述で書ける。
Papa Parse（CSVの読み込み）本文中のカンマ・改行・引用符を正しく扱える定番ライブラリ。
Recharts（グラフ）Reactの部品としてグラフを書け、ツールチップも標準で使える。
Claude API（分類・返信下書き／予定）日本語の文脈理解が必要なため。サーバー側からのみ呼び出し、APIキーを画面に出さない。
Resend（日次メール／予定）無料枠（月3,000通）があり、APIで簡単に送れる。

6. データ設計

読み込めるCSV（列名から自動判別）

項目標準形式口コミコム出力
日付date投稿日時
サイトsite口コミサイト
評価rating（1〜5）★の数（小数あり）
本文textタイトル＋コメント
宿泊タイプstay_type（任意）なし
その他―言語・翻訳コメント・返信内容

読み込み時のルール

  • CSVの最新日を「当日」とする。
  • 外国語の口コミは日本語訳を分析に使い、原文も残す。
  • 本文のない「評価のみ」の投稿は、評価点の集計にだけ使う。
  • 上限：5MB・5,000行（公開URLでの過剰利用対策）。

データの扱い（必ず守る）

  • サンプルはすべて架空（296件・13か月分）。実在の口コミはリポジトリに入れない。
  • データベースは使わず、読み込んだデータは画面を開いている間だけ保持する。

8. AI設計（費用をなるべく抑える）

項目方針
モデルの使い分け開発中の確認はすべて Claude Haiku 4.5。完成版は、分類を Haiku 4.5（入力$1／出力$5・100万トークンあたり）、自然な文章が求められる返信下書きだけ Sonnet 5（$2／$10）。
切り替え方モデル名はコードに書かず環境変数（CLAUDE_MODEL_CLASSIFY／CLAUDE_MODEL_REPLY）で切り替える。未設定なら安い Haiku 4.5 で動く。
開発の順序画面ができるまではAPIを呼ばず、ダミーの結果（USE_MOCK_AI=true）で進め、開発中の費用を0にする。
出力の形決めたJSONの形で必ず返させる機能（Structured Outputs）を使い、分類結果が読めない失敗を防ぐ。
呼び出しを減らす工夫AIで分類するのは今月分だけ（過去の月の評価点はコードで集計）。約20件ずつまとめて送る。返信下書きはボタンを押した1件だけ作る。

9. セキュリティ

  • APIキーは .env.local と Vercel の環境変数だけに置き、.gitignore で .env* をGitHubに上げない。コミット前にキーが含まれていないか毎回確認する。
  • 公開URLからの使いすぎを防ぐため、デモ用パスコード（環境変数）とサーバー側での1日の回数制限を設ける（予定）。
  • ファイルサイズ・行数に上限を設け、画面に出す口コミ本文は文字として表示する（HTMLとして解釈させない）。

10. 開発の進め方と検証

ステップ状態
1. プロジェクト作成・Vercel公開　2. 架空サンプルデータ作成　3. CSV読み込み・一覧　4. 評価点の集計・グラフ　＋口コミコム形式対応完了
5. 4軸分類・アラート・返信の画面（ダミー）　6. Claude APIへの差し替え未着手
7. 日次メール　8. CSV書き出し・利用回数の上限・エラー表示未着手
9. 効果測定　10. 見た目の調整・README・最終公開未着手
  • Git運用：1機能ずつ「動作確認 → コミット → GitHubへプッシュ」。動かない状態はプッシュしない。
  • 検証：型チェック・lint・ビルドに加え、ブラウザを自動操作して確認（不正なCSV、絞り込み、スマホ幅、ダークモード）。集計値は別の計算方法と照合した。
  • 効果測定（予定）：返信作成時間（1件5〜7分→目標1分、10件実測）、分類の精度（架空50件に人が手作業で正解を付け、AIとの一致率を出す）、APIコスト（1件あたり・1施設1か月あたり）。返信下書きは Haiku 4.5 と Sonnet 5 を比較する。

11. 主な設計判断と理由

判断理由
評価点の集計はAIを使わず計算で出す平均・前月比・前年比は計算で正確に出せる。AIを使うと費用がかかり、数字が不正確になるおそれがある。
データベースを使わない期限内に一連の流れを完成させることを優先。CSVをその都度読み込む運用で要件を満たせる。
前提を「1泊中心のホテル・旅館」に修正当初「滞在型（長期滞在）」を前提にしていたが、実際の利用者はほとんどが1泊と分かり、施設設定・サンプルデータを作り直した。
口コミコムの出力CSVに対応現場が実際に使う出力形式をそのまま読めることが、毎日の運用で使われる条件になる。形式の確認は列名と値の形だけで行い、実在の口コミの中身は使っていない。
精度測定の正解は人が付けるAIに正解を付けさせると「AIとAIの比較」になり、精度の測定にならないため。

12. 今後の課題・未決定事項

  • 分類の軸：口コミコムのCSVには独自の4軸（品質・接客・清潔感・雰囲気）の件数が付いている。アプリ独自の4軸でAI分類するか、口コミコムの分類も参考表示するかを、ステップ5の前に決める。
  • Anthropic のAPIキー・Resend のアカウントの準備（ステップ6・7で必要）。
  • 精度測定用の架空50件への正解ラベル付け（ステップ9までに実施）。
